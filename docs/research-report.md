# Rebuild Daneel around flat, gated skills

Late-2026 best practice supports most of the Context Architect design. Short, high-signal instruction files, ADR-governed decisions, clean-context reviewers and human gates are all well supported. Three structural assumptions need to change. First, **no major agent harness discovers a SKILL.md nested inside another skill's folder**. OpenCode says outright that it does not look inside a skill directory, so Daneel's nested files work only as reference leaves that a parent loads by explicit path. They are not skills that can trigger on their own ([OpenCode](https://opencode.ai/docs/skills/); [Claude Code](https://code.claude.com/docs/en/skills)). Second, the security vocabulary has moved on. **OWASP's 2026 LLM Top 10 renumbers the risks**, with Excessive Agency up to LLM03 and System Prompt Leakage renamed Hidden Context Exposure, and the separate Agentic Top 10 (ASI01 to ASI10) now covers coordinators and sub-agents ([OWASP README](https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/README.md); [OWASP GenAI](https://genai.owasp.org/2025/12/09/owasp-top-10-for-agentic-applications-the-benchmark-for-agentic-security-in-the-age-of-autonomous-ai/)). Third, the evidence on orchestration has hardened in favour of restraint. Multi-agent setups cost about **15x the tokens of chat** and **degrade sequential planning by 39 to 70%**, so the default should be one agent, one writer, and parallel workers only where they add read-only intelligence ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system); [Google Research](https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/); [Cognition](https://cognition.com/blog/multi-agents-working)). The 150-word cap is legal and frugal: it is far below every documented limit, but it is Daneel's own convention, not a standard. The sections below take each area in turn and end with a sourced change list for the master version.

## Nested SKILL.md files are reference leaves, not discoverable skills

The Agent Skills specification, which Anthropic published as an open standard in December 2025, requires only two frontmatter fields ([Anthropic Engineering](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)). `name` must be **1 to 64 characters of lowercase letters, digits and single hyphens, and must match the parent directory name**. `description` must be **1 to 1,024 characters and say both what the skill does and when to use it** ([agentskills.io](https://agentskills.io/specification)). The optional fields are `license`, `compatibility`, `metadata` (string keys to string values) and the experimental `allowed-tools`. Anthropic adds that names must not contain "anthropic" or "claude", that neither field may contain XML tags, and that descriptions must be written in the **third person** because they are injected into the system prompt ([Anthropic best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)). Claude Code accepts many extra fields (`when_to_use`, `paths`, `disable-model-invocation`, `context: fork` and others) but silently ignores unknown ones, and claude.ai and the Skills API honour only the six spec fields ([Claude Code](https://code.claude.com/docs/en/skills)). A suite meant to run in Claude Code, Codex and OpenCode should therefore stick to the six portable fields and treat any harness-specific field as an optional extra.

Body size is not a constraint for Daneel. The spec budgets about **100 tokens of metadata per skill at startup, under 5,000 tokens for the body on activation, and under 500 lines** for SKILL.md ([agentskills.io](https://agentskills.io/specification)). A 150-word body is about 200 tokens. The binding constraint is the listing budget instead. Claude Code truncates the combined `description` and `when_to_use` at **1,536 characters** and advises putting the key use case first. Codex gives the whole skills list **2% of the context window** (8,000 characters if the window is unknown) and shortens descriptions, or drops skills, when it runs over ([Claude Code](https://code.claude.com/docs/en/skills); [Codex](https://learn.chatgpt.com/docs/build-skills)). Daneel's descriptions should therefore front-load trigger keywords. Its bodies, by contrast, have room to spare.

Discovery is where the current design breaks. Claude Code looks for `.claude/skills/<name>/SKILL.md` in the start directory and every parent up to the repo root. It loads nested `.claude/skills/` folders lazily when Claude touches files below them ([Claude Code](https://code.claude.com/docs/en/skills)). Codex scans `.agents/skills` from the working directory up to the repo root, plus user and admin locations ([Codex](https://learn.chatgpt.com/docs/build-skills)). OpenCode reads `.opencode/skills`, `.claude/skills` and `.agents/skills`. It allows grouping folders, but states that **"A directory containing `SKILL.md` is one skill. OpenCode does not search inside it for more skills"** ([OpenCode](https://opencode.ai/docs/skills/)). Neither Claude Code nor Codex documents recursion into a skill's own subfolders. Their docs describe supporting files only as things SKILL.md references. Anthropic's authoring guide adds that **all reference files should link directly from SKILL.md**, because chains of nested references lead Claude to read files only partly ([Anthropic best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)).

For Daneel, this means a three-level tree of SKILL.md files gives you a reading order the agent may not follow, not progressive disclosure. The fix is not to abandon short files but to make the topology honest. Each capability that must trigger by itself (ADR authoring, code review, orchestration, security gate) belongs at the top level as `skills/<name>/SKILL.md`. Child files become plain references (`references/<topic>.md`, or child SKILL.md files kept for later promotion), each linked directly from the parent with a one-line "read when" cue. Grouping folders are portable only to OpenCode, so they should be avoided. Two empirical gaps remain: nobody has documented whether Claude Code or Codex would pick up a nested SKILL.md by accident. A quick test in each harness should settle this before the master version ships.

Anthropic's other authoring rules translate directly. Prefer gerund names such as `reviewing-code` or `recording-decisions`, though noun phrases are acceptable if used consistently. Remove dated or "as of" wording from bodies. Use one term per concept. Match the degree of freedom to how fragile the task is, with exact scripts for fragile steps and prose for judgement. Write **three evaluation scenarios before writing documentation**, and test on Haiku, Sonnet and Opus, since a 150-word body that suits Opus may starve Haiku ([Anthropic best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)).

## Always-loaded context should stay under 200 lines and never repeat itself

Anthropic defines context engineering as finding the **"smallest possible set of high-signal tokens that maximize the likelihood of some desired outcome."** It treats attention as a finite budget that degrades as context grows ([Anthropic Engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). Chroma's study of 18 models gives the empirical basis. **Performance falls as input length grows, even on simple tasks.** A single distractor hurts, and four hurt more. A focused prompt of about 300 tokens beat a full prompt of about 113,000 tokens on LongMemEval ([Chroma](https://www.trychroma.com/research/context-rot)). Chroma does not explain the mechanism, but the practical point is sound: plausible but irrelevant guidance in always-loaded files does active harm, beyond wasting tokens. Anthropic's recommended toolkit is just-in-time retrieval through lightweight identifiers, compaction, tool-result clearing, structured notes outside the window, and sub-agents that return **1,000 to 2,000-token summaries** ([Anthropic Engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)).

AGENTS.md is now an open format stewarded by the Agentic AI Foundation under the Linux Foundation. It is a predictable place for build and test commands, code style, testing and security notes, where **the nearest file to the edited code wins and explicit user prompts override everything** ([agents.md](https://agents.md/)). Codex concatenates files from the git root down to the working directory and stops at **32 KiB** by default ([Codex](https://learn.chatgpt.com/docs/agent-configuration/agents-md.md)). Claude Code does not read AGENTS.md natively. It needs an `@AGENTS.md` import in CLAUDE.md or a symlink. Anthropic's own target is **under 200 lines per CLAUDE.md**, because "longer files consume more context and reduce adherence". Procedures belong in skills or path-scoped `.claude/rules/`, and `@imports` save no context because they expand at launch ([Claude Code memory](https://code.claude.com/docs/en/memory)).

Memory files follow the same discipline. Claude Code auto-loads the first **200 lines or 25 KB of MEMORY.md**, treating it as an index whose topic files are read on demand ([Claude Code memory](https://code.claude.com/docs/en/memory)). Hermes Agent caps MEMORY.md at **2,200 characters** and USER.md at **1,375 characters**. It injects them as a frozen snapshot at session start, rejects writes over the cap so the agent must consolidate (it recommends doing so at 80% use), scans entries for injection, and forbids duplicating what is already in SOUL.md or AGENTS.md ([Hermes memory](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory)). Anthropic's memory tool truncates views above 16,000 characters and advises capping file sizes, expiring stale files and stripping sensitive data. It also gives a multi-session pattern: read the progress log and feature checklist first, work on one feature, update both at the end ([Claude memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)).

Together these sources suggest a clean division of responsibility for Daneel. SOUL.md holds identity and voice only. USER.md holds a profile of about 1.4k characters. MEMORY.md holds durable learned facts and an index, capped at about 2.2k characters or 200 lines. AGENTS.md holds project commands and conventions in under 200 lines, with CLAUDE.md reduced to an `@AGENTS.md` import plus any Claude-only notes. Skills hold procedures. One caveat: SOUL.md and USER.md are Hermes and OpenClaw conventions, not a cross-vendor standard, so a portable suite should not depend on them being loaded.

## MADR 4.0 plus explicit status semantics makes ADRs safe for agents

The ADR core has barely moved since Nygard's 2011 post: Title, Context, Decision, Status and Consequences, numbered sequentially and never reused, one or two pages long, and **kept but marked superseded rather than deleted** ([Cognitect](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions)). The current structured template is **MADR 4.0.0, released 17 September 2024, with no later release by November 2026** ([adr.github.io/madr](https://adr.github.io/madr); [MADR changelog](https://raw.githubusercontent.com/adr/madr/main/CHANGELOG.md)). Its mandatory sections are Context and Problem Statement, Considered Options and Decision Outcome. The optional sections are Decision Drivers, Consequences, Confirmation, Pros and Cons of the Options and More Information. Front matter is optional and covers `status`, `date`, `decision-makers`, `consulted` and `informed`. Files are named `NNNN-title-with-dashes.md` and stored in `docs/decisions/` ([adr.github.io/madr](https://adr.github.io/madr)). Zimmermann's primer adds three conventions: list the chosen option first, write consequences as "Good, because" and "Bad, because", and use Confirmation to record how the decision will be enforced through reviews or tests ([ozimmer.ch](https://ozimmer.ch/practices/2022/11/22/MADRTemplatePrimer.html)). YADR, a YAML and JSON Schema port of MADR published in June 2026, offers machine validation, but nobody has shown it is widely adopted yet ([ozimmer.ch YADR](https://ozimmer.ch/practices/2026/06/19/YADRTemplateIntroduction.html)).

The institutional guidance gives a usable trigger list for "is an ADR needed?". AWS lists decisions on structure, non-functional requirements, dependencies, interfaces and construction techniques ([AWS](https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/adr-process.html)). Microsoft adds anything **"difficult to reverse"** and asks for a stated **confidence level** ([Microsoft](https://learn.microsoft.com/en-us/azure/well-architected/architect-role/architecture-decision-record)). Google adds any question with no existing precedent, or with two or more viable options ([Google Cloud](https://docs.cloud.google.com/architecture/architecture-decision-records)). The GOV.UK framework scales approval by blast radius, from team to cross-team, department-wide and cross-government ([GOV.UK](https://www.gov.uk/government/publications/architectural-decision-record-framework/architectural-decision-record-framework)). GDS Way makes the pull request the lifecycle: an open PR is Proposed and a merge is Accepted ([GDS Way](https://gds-way.digital.cabinet-office.gov.uk/standards/architecture-decisions.html)). Zimmermann's ecADR definition of done requires evidence, at least two alternatives compared against drivers, peer agreement, lean documentation, and a planned realisation check and revisit point. His anti-pattern catalogue names Dummy Alternative, Free Lunch Coupon, Mega-ADR and Blueprint in Disguise as failures ([ecADR](https://ozimmer.ch/practices/2020/05/22/ADDefinitionOfDone.html); [ADR creation](https://ozimmer.ch/practices/2023/04/03/ADRCreation.html)).

Mutability is the one live disagreement. AWS, Microsoft and Nygard treat accepted ADRs as immutable and append-only, superseded only by a new, linked record ([AWS](https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/adr-process.html); [Microsoft](https://learn.microsoft.com/en-us/azure/well-architected/architect-role/architecture-decision-record)). Henderson reports that "mutability has worked better for our teams" ([Henderson](https://github.com/joelparkerhenderson/architecture-decision-record)). Davidson, writing about coding agents in October 2026, shows why the choice matters for Daneel. **Agents over-apply stale accepted ADRs**, for example by building a compatibility layer around an obsolete storage abstraction instead of flagging the conflict, and agent edits bloat records with deliberation. His fix is to declare in AGENTS.md that accepted ADRs are binding, proposed ones are context and superseded ones are history, and to tell the agent to **stop and propose a new ADR when a task conflicts** with an accepted one ([O'Reilly Radar](https://oreilly.com/radar/coding-agents-love-decision-records/)). The reconciliation that satisfies both camps is to keep accepted ADRs immutable in substance, supersede them with bidirectional links, keep a status index so the agent can see what is in force, and write the binding semantics into AGENTS.md. Davidson's piece is practitioner opinion, and no vendor guidance on ADRs as agent context exists yet.

## Code review should judge code health, label severity and leave approval to humans

Google's standard remains the reference point. Approve once a change **"definitely improves the overall code health"**, even if it is imperfect. Review design first, then functionality, complexity, tests, naming, comments, style and context. Never block on personal style. Respond within one business day ([Google standard](https://google.github.io/eng-practices/review/reviewer/standard.html); [What to look for](https://google.github.io/eng-practices/review/reviewer/looking-for.html)). Changes should be small: **about 100 lines is reasonable and 1,000 is usually too large**, and reviewers may reject oversized changes outright ([Google small CLs](https://google.github.io/eng-practices/review/developer/small-cls.html)). SmartBear's Cisco-derived figures point the same way. Review 200 to 400 lines at a time, below 500 lines an hour, and for no more than 60 minutes. These are vendor figures, so treat them as a direction, not a precise limit ([SmartBear](https://smartbear.com/learn/code-review/best-practices-for-peer-code-review/)). Bacchelli and Bird found that review catches fewer defects than people expect, and that **"code and change understanding is the key aspect"** ([Microsoft Research](https://microsoft.com/en-us/research/?p=164195)). That points an AI reviewer towards explaining intent and blast radius, not just generating comments.

Conventional Comments gives a machine-parseable output format, `<label> [decorations]: <subject>`. Its labels include praise, nitpick, suggestion, issue, question and note, and its decorations are blocking, non-blocking and if-minor. Its rule to **use a question instead of an issue when unsure** suits an AI reviewer well ([conventionalcomments.org](https://conventionalcomments.org/)). It maps cleanly onto Google's Nit, Optional and FYI labels ([Google comments](https://google.github.io/eng-practices/review/reviewer/comments.html)).

The evidence on AI-assisted development is mixed, and Daneel's review skill should assume the worst cases are real. DORA 2025 finds AI adoption now correlates positively with throughput but **"still shows a negative relationship with software delivery stability"**, and calls AI an amplifier of whatever practices a team already has ([DORA 2025](https://cloud.google.com/blog/products/ai-machine-learning/announcing-the-2025-dora-report?e=48754805)). GitClear's 2026 data shows duplicated blocks **up 81%**, refactored ("moved") code falling from 21% to 3.8% of changed lines, and **error-masking constructs up 47%**. The data is correlational and the page has internal inconsistencies ([GitClear](https://gitclear.com/the_ai_code_quality_maintainability_gap)). METR's randomised trial found experienced developers **19% slower with AI** while believing they were faster. Its February 2026 follow-up is inconclusive, and METR itself calls it very weak evidence ([METR 2025](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/); [METR 2026](https://metr.org/blog/2026-02-24-uplift-update/)). Thoughtworks puts "complacency with AI-generated code" on Hold, citing larger change sets, automation bias and review fatigue ([Thoughtworks](https://www.thoughtworks.com/radar/techniques/complacency-with-ai-generated-code)).

Vendor AI reviewers have converged on one design. Anthropic's Code Review runs parallel bug-hunting agents, **verifies findings to filter false positives**, ranks them by severity, scales depth with PR size, and **"does not approve PRs"** ([Anthropic](https://claude.com/resources/articles/code-review)). Its under-1% incorrect rate is self-reported. GitHub warns that Copilot review can hallucinate and miss problems in large changes, and that it must be supplemented by human review ([GitHub Docs](https://docs.github.com/en/copilot/responsible-use/code-review)). For agent-written PRs, the evidence says to look hardest at duplication versus reuse of existing helpers, swallowed errors and silent fallbacks, tests that would not fail if the code broke, and PR size.

Recurring comments should become machine checks. Architectural fitness functions assess architectural characteristics automatically ([Thoughtworks](https://www.thoughtworks.com/en-gb/radar/techniques/architectural-fitness-function)). Notion's ratchet records allowed violation counts per rule and file, blocks any increase, and lets counts only fall ([Notion](https://www.notion.com/blog/how-we-evolved-our-code-notions-ratcheting-system-using-custom-eslint-rules)). Fowler's debt quadrant classifies debt as prudent or reckless and deliberate or inadvertent ([Fowler](https://martinfowler.com/bliki/TechnicalDebtQuadrant.html)). Reckless debt should block a change, and prudent deliberate debt should carry a tracking item. No study yet measures how ratchets affect defect rates, so this is practitioner consensus rather than proven effect.

## Orchestration works when writes stay single-threaded and loops have hard brakes

Anthropic and OpenAI give the same opening advice: **start with the simplest thing that works** and maximise a single agent before splitting ([Anthropic](https://www.anthropic.com/engineering/building-effective-agents); [OpenAI](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)). Anthropic's five patterns each fit a task shape. Use prompt chaining for fixed subtasks, routing for distinct categories, parallelisation for independent or voting work, orchestrator-workers when subtasks cannot be predicted, and evaluator-optimiser when clear criteria exist. OpenAI adds that overlapping tools, not their number, are the trigger for splitting, and that tool descriptions should be fixed first.

The quantitative case for restraint is now strong. Anthropic's research system beat a single agent by **90.2%** on breadth-first research. Token spend alone explained 80% of the variance, multi-agent runs used **about 15x** the tokens of chat, and Anthropic named coding as a poor fit because few coding tasks are truly parallelisable ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)). Google's 180-configuration study found **+80.9%** for centralised coordination on parallelisable finance tasks. It found **minus 39 to 70% on sequential planning**, **17.2x error amplification for independent agents** against 4.4x for centralised ones, and diminishing or negative returns once a single agent already scores above about 45% ([Google Research](https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/); [arXiv](https://arxiv.org/html/2512.08296v2)). Cognition's April 2026 revision of "Don't Build Multi-Agents" settles on agents that **"contribute intelligence to a task while writes stay single-threaded"**: clean-context reviewers, read-only search subagents, consulting a stronger model, and manager-child map-reduce. Parallel-writer swarms and unstructured agent networks still fail ([Cognition](https://cognition.com/blog/multi-agents-working)).

Delegation needs a written contract because the worker starts blank. Claude Code subagents get **a fresh context window that does not see the conversation history**, work only from the delegation message, and return only a summary ([Claude Code subagents](https://code.claude.com/docs/en/subagents)). Anthropic found subagents duplicated work and left gaps unless each brief named **an objective, an output format, tool and source guidance, and clear task boundaries**. Its effort rules scale from one agent making 3 to 10 calls for simple facts to more than 10 subagents for complex research, and outputs go to external storage, with lightweight references passed back ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)). Platform controls enforce boundaries more reliably than prose: `tools` allowlists, `permissionMode`, `maxTurns` (which returns partial output), `isolation: worktree`, and hooks that can block commands. Nesting now defaults to three levels and can be capped with `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` ([Claude Code subagents](https://code.claude.com/docs/en/subagents)).

The Berkeley MAST taxonomy shows which brakes matter. Across 1,642 traces, the commonest failures are **step repetition (15.7%), reasoning-action mismatch (13.2%), unawareness of termination conditions (12.4%) and disobeying the task spec (11.8%)**. Verification failures make up about a quarter. Better role specs and an objective-verification step improved success by only about 9.4% and 15.6% ([arXiv](https://arxiv.org/html/2503.13657v3)). Anthropic's long-running harnesses supply the working pattern. Keep state on disk in a progress file, a JSON feature list that the agent may only flip from failing to passing, and git commits. Work on **one feature per session**. Use a separate sceptical evaluator, because generators "confidently praise" their own work. Agree sprint contracts on success criteria before work starts. Revisit scaffolding as models improve, since every component "encodes an assumption about what the model can't do" ([Anthropic harnesses](https://anthropic.com/engineering/effective-harnesses-for-long-running-agents); [Anthropic harness design](https://anthropic.com/engineering/harness-design-long-running-apps)). The full harness cost **over 20x** a solo run, so budget caps are not optional. OpenAI adds exit conditions (a tool call, structured output, an error or a maximum number of turns) and escalation to a human after retry thresholds or before irreversible actions ([OpenAI](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)). No primary source recommends specific numeric caps, so Daneel must choose its own and say so.

## Security now means OWASP 2026 IDs, the Rule of Two and gates that show the raw action

OWASP published the **2026 LLM Top 10 on 4 August 2026**. Its order is LLM01 Prompt Injection, LLM02 Sensitive Information Disclosure, LLM03 Excessive Agency, LLM04 Supply Chain, LLM05 Data and Model Poisoning, LLM06 Unbounded Consumption, LLM07 Misinformation, LLM08 Hidden Context Exposure, LLM09 Vector and Embedding Weaknesses and LLM10 Improper Output Handling ([OWASP README](https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/README.md)). Its framing is to stop trying to build a model that cannot be fooled and instead **build the system around it** ([Help Net Security](https://www.helpnetsecurity.com/2026/08/06/owasp-2026-llm-top-10-released/)). Any Daneel file citing "LLM06:2025 Excessive Agency" or "LLM07:2025 System Prompt Leakage" is now out of date. The 2025 per-item pages still give the best mitigation detail, including that the system prompt is not a secret and that **authorisation must be deterministic, auditable and enforced outside the LLM** ([OWASP LLM07:2025](https://genai.owasp.org/llmrisk/llm072025-system-prompt-leakage/)). For a coordinator, the Agentic Top 10 matters more. It covers ASI01 Goal Hijack, ASI02 Tool Misuse, ASI03 Identity and Privilege Abuse, ASI04 Agentic Supply Chain, ASI06 Memory and Context Poisoning, ASI07 Insecure Inter-Agent Communication, ASI08 Cascading Failures and ASI09 Human-Agent Trust Exploitation. ASI09 describes how **"polished, confident explanations"** lead operators to approve harmful actions ([OWASP GenAI](https://genai.owasp.org/2025/12/09/owasp-top-10-for-agentic-applications-the-benchmark-for-agentic-security-in-the-age-of-autonomous-ai/)).

Architectural constraints beat filters. Meta's **Agents Rule of Two** says a session should combine at most two of three properties: untrusted input, access to sensitive systems or data, and the ability to change state or communicate externally. A task needing all three requires human approval or another reliable check ([Meta](https://ai.meta.com/blog/practical-ai-agent-security/)). This extends Willison's lethal trifecta ([Willison](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)). The reason detection is not enough: "The Attacker Moves Second", by authors from OpenAI, Anthropic and Google DeepMind, found that **most of 12 published defences failed against more than 90% of adaptive attacks**, and human red-teamers beat all of them ([arXiv](https://arxiv.org/abs/2510.09023)). NIST's CAISI competition found at least one successful attack against every one of 13 frontier models ([NIST](https://www.nist.gov/blogs/caisi-research-blog/insights-ai-agent-security-large-scale-red-teaming-competition)). The UK NCSC calls the LLM an "inherently confusable deputy" whose risk "may never be fully mitigated". It advises limiting tools, using deterministic safeguards, avoiding deny-lists and logging every input, output and tool call. It also endorses dropping an LLM's privileges to those of the **least-trusted party whose content it processes** ([NCSC](https://www.ncsc.gov.uk/blog-post/prompt-injection-is-not-sql-injection)). Beurer-Kellner et al. offer six design patterns. The most useful for Daneel are Plan-Then-Execute, LLM Map-Reduce, where isolated workers return constrained outputs, and Context-Minimisation ([arXiv](https://arxiv.org/abs/2506.08837v3)).

A code-review agent nearly always has untrusted input (diffs, issues, dependency code) and sensitive access (the repo and CI), so the Rule of Two says it should lack the third property. **Pushing, merging, posting externally and network egress belong behind a human gate.** Those gates must be few. Anthropic found users **approve 93% of permission prompts**. Sandboxing that isolates both filesystem and network cut prompts by 84%. Anthropic's auto-mode classifier deliberately strips assistant prose and tool results "so the agent can't argue its way past" ([Anthropic auto mode](https://www.anthropic.com/engineering/claude-code-auto-mode); [Anthropic sandboxing](https://www.anthropic.com/engineering/claude-code-sandboxing)). Even that classifier missed 17% of real overeager actions, and Anthropic says it does not replace careful human review on high-stakes infrastructure. A human gate should therefore show the concrete command, diff, target and blast radius rather than the agent's justification. It should never treat text inside a tool result or sub-agent message as approval.

Skills themselves are an attack surface, which matters for a skill suite. An analysis of 31,132 marketplace skills found **26.1% with at least one vulnerability**, and skills that bundle scripts were 2.12x more likely to be vulnerable ([arXiv 2601.10338](https://arxiv.org/html/2601.10338v1)). A study of 157 confirmed malicious skills found **84.2% of their vulnerabilities in the natural-language SKILL.md rather than in code**. Some targeted the platform itself through hooks, permission flags and model substitution, and comparing documented with observed behaviour was the best detector ([arXiv 2602.06547](https://arxiv.org/html/2602.06547v1)). MCP tool descriptions can hide instructions, change after approval ("rug pulls") and shadow other servers' tools. The mitigations are to pin by hash and display full descriptions ([Invariant Labs](https://invariantlabs.ai/blog/mcp-security-notification)). Daneel's security skill should audit instruction prose as closely as scripts. Its own files should contain no secrets, no remote script fetches and no unpinned dependencies.

## Conclusion

The research reframes what Daneel is for. Its value lies less in packing guidance into many small files and more in deciding which few tokens load when, and in enforcing the boundaries prose cannot. Every strand points the same way. Context rot argues for less always-loaded text. Discovery rules argue for a flat set of real skills with leaves read by path. The orchestration studies argue for one writer and independent verifiers. The security literature argues that controls must sit outside the model. A master version built on these lines would move rules out of prose and into structure: frontmatter that validates, delegation contracts that platforms enforce, ratchets in CI, ADR status that agents can read, and gates that show the action rather than the argument.

The second implication concerns maintenance. Much of what Daneel encodes is scaffolding that "encodes an assumption about what the model can't do", and Anthropic has already removed sprints and per-step evaluation as models improved. OWASP renumbered its list within a year, and Claude Code changed its subagent nesting default three times across releases. The suite should therefore keep volatile facts in dated reference files and evals in the repo, and should schedule a review of its own skills, which is the same revisit discipline it asks of ADRs.
